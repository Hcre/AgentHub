## 关键决策

| 决策 | 原因 | 影响 |
|---|---|---|
| 选 Tauri 2 而非 Electron | 包体 3-5MB vs 100MB+;AgentHub 后端已吃内存,前端壳不再叠 Chromium | 零经验团队需接受少量 Rust(scaffold 出的代码 80% 不改) |
| 选 Tauri 2 而非 Capacitor | 桌面端性能 / 包体 / 三端覆盖更优;Capacitor 移动端更强(但我们不做移动) | 同上 |
| 选 M2 瘦客户端而非 M1 Sidecar | 包体小 200MB+ → 3-5MB;后端零修改;用户部署体验不变 | 用户必须同时装 backend + App,首启失败率较高 → §3.1 引导页缓解 |
| 选 M2 瘦客户端而非 M3 全栈换骨 | M3 违反 ADR-0001 CLI 优先,后端是 AgentHub 真正壁垒 | - |
| 不进任何商店 | 0 费用 + 0 审核 + 0 包跡合规;开源早期迭代节奏 > 商店触达 | macOS Gatekeeper / Windows Defender 需文档引导 + 后续签名 |
| 不做移动端 | 现有三栏布局是桌面设计,1:1 搬到桌面零改造;移动端需重排 + 双套代码 | 短期内放弃移动用户,可作为 P2 roadmap 项 |
| 后端零修改 | 9 个 router / WS / mcp / skills / memory 全部沿用;2 年工程积累不被背叛 | 启动时 App 必须能探测到用户 backend,这是设计上的硬约束 |

### B 线:Review 通过后启动(5-7 周)

按规格 §5 阶段划分(详见 ADR-0007 §五),阶段 0 → 1 → 2 顺序执行:
- 阶段 0(1-2 天):建 `feature/desktop/tauri-scaffold` 分支,`npm create tauri-app@latest`
- 阶段 1(1 周):Tauri 套壳 + 复用 AppShell + 设置页
- 阶段 2(1 周):backend 健康探测 + JWT 存储 + 动态 baseURL

**关键避坑提示**:
- Tauri 2 scaffold 出的 Rust 代码 **不要**大改,保持默认
- macOS 第一次跑 dev 模式会问权限(摄像头/麦克风等),拒绝即可,我们用不到
- `tauri.conf.json` 里 `app.windows[0].width/height` 是 CSS 像素,不是物理像素
- Windows 上 `tauri build` 需要装 WebView2 Runtime(Win11 自带,Win10 用户要手动)
- Linux 上 AppImage 需要 fuse 库,Ubuntu 22.04+ 自带

### 容易踩的坑(基于 web 端经验推测)

- 后端 health 端点被前端频繁轮询可能拖慢,记得前端做 30s 节流(规格 §2.1 探测时机已规定)
- 三栏布局在窗口 < 1024px 时会挤出(规格 §4.1 最小尺寸已规定,但实际可能需要 media query 收一收)
- 用户的 backend URL 可能是内网穿透(frp / cloudflared),WS 在 WebView 下可能因反代 timeout 断,要做心跳

## 临时约定(可能后续调整)

- 桌面 App 仓库路径:**沿用同一个 monorepo**,在 `src/desktop/` 下(等代码开发时确认是否独立 repo)
- 桌面 App 版本号跟随根 `package.json` 的 `version`
- 桌面 App 用户与 web 端用户共用同一后端账号体系(JWT)
- Tauri 2 锁定的具体小版本在 scaffold 时确认(若 2.0 stable 已发即锁 2.0.0)
