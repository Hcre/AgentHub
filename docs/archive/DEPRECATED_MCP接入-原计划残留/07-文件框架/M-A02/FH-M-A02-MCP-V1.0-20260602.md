## DD-M 洞察（每轮 ≥ 1 条）

### 洞察-1：handlers 拆分的测试隔离价值
[M-A02 洞察] MD-M-A02 提及「单元 + 集成（多客户端订阅）18 用例」——handlers 拆分为 connect/subscribe/ping 三文件后，每个 test_*.py 可独立 mock 单一 handler，避免 fixture 污染；sticky session 重连场景测试可单独 patch connect 不影响 subscribe。

### 洞察-2：跨模块依赖的注释透明性
[M-A02 洞察] subscription_store 跨 M-D03/M-D01 调用、offline_queue 跨 M-D03、bus_listener 跨 M-EV01 —— 这些跨模块依赖已在文件头注释的「依赖关系」段明确标注「跨模块（仅通过接口调用，不直接依赖实现）」，避免下游 DD-S 误将 M-D03/M-EV01 的实现塞入 M-A02。

### 洞察-3：BusListener 推送方向与 handlers 解耦
[M-A02 洞察] handlers 处理 client → server（上行消息），BusListener 处理 server → client（下行推送）。两者方向不同，BusListener 直连 WSServer.emit 而非绕行 handlers 是 Observer 模式的正确落地，避免循环依赖。

### 洞察-4：OfflineQueue.replay_missed 幂等性
[M-A02 洞察] 客户端重连后 replay_missed 同 since 二次调用必须返回 0，否则会重复推送。IC-002 时序图标注「断线 → Client 重连 → WSGateway 回放 Redis Stream」，但未显式说明幂等性；本框架在函数注释中显式标注「重复调用同 since 返回 0」，避免下游实现时遗漏。

### 洞察-5：ping_timeout 与 socketio 配置一致性
[M-A02 洞察] MD-M-A02 §状态机「ping_timeout(30s)」与 socketio.AsyncServer(ping_timeout=30) 必须保持严格一致；mark_timeout 巡检周期 5s 须与 ping_timeout 协调（5s < 30s，确保 6 次巡检窗口内必有 1 次发现）。注释中已显式说明。
