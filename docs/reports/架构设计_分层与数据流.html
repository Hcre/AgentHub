§9 数据流

协调者分解与 DAG 执行

DAG 编译

Coordinator 输出的 JSON 决策： { "plan": { "tasks": [ {"id": "t1", "title": "前端UI组件", "assignee": "FrontendAgent", "dependencies": []}, {"id": "t2", "title": "后端API", "assignee": "BackendAgent", "dependencies": []}, {"id": "t3", "title": "集成测试", "assignee": "ReviewerAgent", "dependencies": ["t1", "t2"]} ] } } Harness 校验规则： ✓ 检测循环依赖 → detect_cycle(plan) → 拒绝 ✓ 所有 assignee 在群组内 → 不在则警告 ✓ 依赖 ID 都存在 → 缺失则补充 ✓ 通过后 → 创建 Task 聚合根 + 子任务 + 入队

依赖与并行

▶
无依赖 → 并行执行：t1（前端）和 t2（后端）无依赖关系，同时分配 Worker 执行。
有依赖 → 串行等待：t3（集成测试）依赖 t1、t2 都完成后才进入 RUNNING 状态。

实现要点

L3 Service 事务边界

class AgentService: async def create(self, cmd: CreateAgentCommand) -> AgentResponse: # 1. 领域校验（L2） if await self.agent_repo.exists_by_name(cmd.name): raise DomainError("Agent name already exists") # 2. 创建聚合根（L2） agent = Agent( name=cmd.name, avatar=cmd.avatar, role=cmd.role, provider=cmd.provider, model=cmd.model, api_key_encrypted=encrypt(cmd.api_key), # L3 负责加密 ) # 3. 持久化（L1） await self.agent_repo.save(agent) # 4. 发布事件 await self.event_bus.publish(AgentCreated( agent_id=agent.id, name=agent.name, timestamp=datetime.utcnow(), )) return AgentResponse.from_domain(agent)

关键设计决策

为什么用 Docker Compose 不用 K8s？

MVP 阶段需要最简单的部署方案。Docker Compose 一台机器即可跑通全部 5 个服务（前端/后端/PG/Redis/Celery），减少运维心智负担。

为什么异步优先？

WebSocket + 流式输出 + LLM 调用全部是 IO-bound。FastAPI 原生 async + SQLAlchemy 2.0 async 模式 + async Redis 客户端，全程非阻塞。

为什么不使用 LangChain 框架？

LangChain 抽象层过厚，调试困难。自研 UnifiedAgent + Harness 架构更轻量、可测试、可推理。

为什么四道硬闸防止 token 爆炸？

LLM token 消耗直接关系到成本。硬闸：最大步骤数 / 最大 Token / 最大执行时长 / 最大工具调用次数，任一超限则终止。
