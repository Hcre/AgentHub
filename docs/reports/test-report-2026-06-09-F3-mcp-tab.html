§3 新 bug 暴露: workspace_id UUID 不匹配

!
症状:MCP tab 选 active conversation 后,GET /api/mcp/market?workspace_id=cmq5ezout8cm3 返回 422 UUID parsing error
真因:useUIStore.activeConversationId 存的是 chatStore 的 conversation ID(前端 nanoid 风格 cmq5ezout8cm3 12 字符),但 MCP 后端 workspace_id schema 是 strict UUID
架构冲突:chat 域的 conversation ID 与 workspace 域的 workspace ID 是两个独立 ID 空间,前端直接把 conversation ID 当 workspace_id 传后端 → 422

3.1 修法 (3 选 1, 留 P3+ 决策)

方案改动代价选
A. 改 MCP backend: workspace_id 接受 str (alias session_id 或 conversation_id)1 文件 Pydantic schema 放宽 + 路由层加兼容低 (1-2h)短期
B. 前端: chatStore 加 workspace_id 字段, 创 session 时同时拿 backend session UUIDchatStore + 4 调用点中 (4-6h)中期
C. 改 ID 空间: 统一用 UUID (chat conversation 也存 UUID)全栈重构 (数据迁移)高 (2-3d)长期

建议:短期走 A (后端 schema 接受 str, 内部 map);中长期走 B 统一 ID 空间。本次不动,留工单。

3.2 影响范围

  • F3 (MCP 市场 / 安装 / 绑定) — 整组不可用,需方案 A 才能跑通
  • F2 已有 mcp installation 数据 — 不受影响 (后端 ID 空间独立)
  • F1 市场 list — 同 F3,方案 A 必走
