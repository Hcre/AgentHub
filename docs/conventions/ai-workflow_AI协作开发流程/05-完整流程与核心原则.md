# AI 协作开发流程 — 完整流程与核心原则

## 完整流程总览

```
零、调研
  └─ 产出 → docs/research/

一、计划
  1. 流程笔记 (docs/plan/背景.md)
  2. 功能拆分 (STATUS.md)
  3. BDD 规格 (docs/specs/)
  4. 技术选型 (STATUS.md 中标注)
  5. DeepSeek 讨论完善（概念卡壳对话 5 轮以上仍未理解，才为该问题建专门笔记文件）
  6. DeepSeek 生成计划提纲 (STATUS.md)
  7. Opus 交叉审查 (附仓库状态)
  8. 创建基础设施 (git/STATUS/日志/仪表盘)

二、开发（功能点循环）                              ← 每个功能点完成 → 功能点汇报（对话内联，不落盘）
  ┌─────────────────────────────────┐
  │ 0. 扫描仓库 → 更新 CLAUDE.md     │
  │ 1. Opus 实现                    │
  │ 2. 可观测验证（必须）               │
  │ 3. DeepSeek 审查 diff              │
  │ 4. 你确认差异点                     │
  │ 5. 更新 worklog + STATUS               │
  │ 6. Git commit + tag               │
  │ 7. 3 分钟回顾                      │
  └─────────────────────────────────┘
            ↓
    累计完成 N 个功能点？
       ├─ 否 → 下一个功能点
       └─ 是 → 进入第三步                 ← 收束节点 → 档位二：收束汇报

三、收束（功能批次闸门）                            ← 产出 → 档位二收束汇报
  ┌─────────────────────────────────┐
  │ 阶段1: 文件与代码整理              │
  │ 阶段2: 集中测试                    │
  │ 阶段3: 规范合规审计（AI + 人双线）  │
  │ 阶段4: 效果验证                    │
  │ 产出: 收束报告 → 更新 STATUS.md    │
  └─────────────────────────────────┘
            ↓
     下一个功能点（下一批次）
```

> 汇报两档贯穿全流程：每个功能点→功能点汇报（默认对话内联、不落盘）、收束节点→收束报告（落盘）。详见 `07-汇报.md`。
```

---

## 核心原则

1. **不越界** — 一次只做一个功能点，不扩展到其他范围
2. **不黑盒** — 每个功能点必须留下可观测的客观证据，不开盲盒
3. **不断档** — 每个功能点完成时更新所有记录文件，下一个人能无缝接手
4. **不拖欠** — 回顾中发现的技术债记录到 STATUS，下个循环优先处理
5. **不积压** — 到达计划预设的收束节点必须执行收束（整理代码、审计合规、验证效果）。收束节点是计划时预设的硬闸门：到点未收束，**AI 拒绝开始下一个功能点**（人不必手动卡，AI 自动拦截，但收束本身仍由人触发执行）

## AgentHub 流程红线（PR-01 ~ PR-09）

> 流程节点不只是约定，而是有红线的强制规则。AgentHub 完整 PR-01 ~ PR-09 红线见 [10-process-rules_流程红线全集](../10-process-rules_流程红线全集.md)。

| # | 红线 | 触发于本流程的哪一步 |
|---|------|--------------------|
| **PR-01** | 接口先行：L4 API endpoint + Request/Response Schema 在实现前冻结；变更需 2 人 Review | 第一步 §3 BDD 规格 + 第二步 §1 实现前 |
| **PR-02** | 分支命名 `feature/<domain>/<desc>`；禁直接 push `main` | 第二步 §6 Git commit |
| **PR-03** | Conventional Commits；禁 `WIP`/`fix bug`/`update code` 模糊提交 | 第二步 §6 Git commit |
| **PR-04** | Agent 写文件必经审批：生成 unified diff → 推送审批卡片 → 用户 APPROVE 后才应用 | 第二步 §1 实现（Agent 操作） |
| **PR-05** | 每里程碑结束全员集成测试，按 PRD §九 成功闸门逐项检查 | 收束节点 阶段 4 效果验证 |
| **PR-06** | PR ≥ 1 Approve 才能合并；跨域接口变更 ≥ 2 人（含被影响域 owner） | 第二步 §6 Git commit |
| **PR-07** | 提交前跑 `verify.{bat,sh}`（ruff + pytest cov ≥80 + tsc + eslint）；不通过禁提 PR | 第二步 §3 审查前 |
| **PR-08** | 改代码后必更新 `docs/plan/开发清单_roadmap.md` 验收状态（✅ + 完成日期 + 关键决策） | 第二步 §5 更新 worklog |
| **PR-09** | SPEC 和代码同步：架构变更先改 `docs/specs/01-architecture_架构定义.md`；数据模型变更先改 `docs/specs/03-data-model_数据模型.md` + Alembic；API 变更先改 `docs/specs/04-commands_命令接口.md` | 第二步 §1 实现前 |

> 这些红线是**流程上的硬闸门**：违反 = 流程违规，PR 不可合并。
> AgentHub 自动化校验：`scripts/check_worklog.py`（PR-08）+ `scripts/check_branch.py`（PR-02）+ `scripts/check_docs.py`（PR-09 文档命名）+ pre-commit 钩子（PR-03/PR-07）。
