# 群聊记忆系统 — 高效组织形式探索

> 调研日期：2026-05-23 | 基于 30+ 项目/论文的系统性调研

---

## 一、核心发现：记忆组织 > 记忆存储

调研覆盖了 CrewAI、MetaGPT、ChatDev、AutoGen、Letta/MemGPT、Cognee、Mem0、OpenAI Swarm、bMAS 黑board、CCPM 等 30+ 项目/论文的方法。**最重要的发现来自 Letta 团队（Aug 2025）**：

> "What matters is whether the agent can effectively use the retrieval tool — exact retrieval mechanism (graphs vs. vectors) matters less than agent capabilities."

**简单说：Agent 能不能用好记忆，比记忆本身用什么存储（向量/图/文件）更重要。** 这意味着设计重点应该是记忆的**访问接口**和**组织形式**，而不是底层存储引擎。

---

## 二、社区七大记忆模式

| # | 模式 | 代表项目 | 核心思想 | AgentHub 适配度 |
|---|------|---------|---------|:---:|
| 1 | **提取存储型** | Mem0 | LLM 自动从对话中提取事实，存向量库 | ⭐⭐ |
| 2 | **图基型** | Cognee, Zep/Graphiti | 实体关系图 + 时序版本控制 | ⭐⭐⭐⭐ |
| 3 | **流基型** | Generative Agents | 观测流，按 recency/importance 打分 | ⭐⭐⭐ |
| 4 | **Agent 自管型** | Letta | Agent 自己调用 memory 函数管理自己的记忆 | ⭐⭐⭐⭐⭐ |
| 5 | **时序优先型** | Graphiti | 每个事实带 4 个时间戳，知道"什么时候是真的" | ⭐⭐⭐ |
| 6 | **平台型** | RedPlanet CORE | 统一记忆 + 工具包，多 Agent 共享 | ⭐⭐⭐ |
| 7 | **上下文窗口管理型** | Neural Paging | 代理层压缩/索引对话历史 | ⭐⭐ |

**对 AgentHub 最有价值的是 #2（图基）和 #4（Agent 自管）的混合。**

## 三、最有参考价值的项目详解

### 3.1 CrewAI — 作用域树（Scope Tree）⭐⭐⭐⭐⭐

CrewAI v1 完全重写了记忆系统，从"存储"升级为"认知过程"。核心创新：**记忆作用域树**。

```
/                                    ← 根作用域
├── /group/decisions/                 ← 群组决策（共享，all agents readable）
│   ├── "2026-05-23: 选择 FastAPI 做后端框架"
│   └── "2026-05-23: JWT 过期时间设为 7 天"
├── /group/tasks/                     ← 任务状态（共享）
│   ├── task-1: COMPLETED
│   └── task-2: RUNNING
├── /agent/pm/working/               ← PM Agent 的工作记忆（私有）
│   └── "当前在分解博客系统需求..."
├── /agent/engineer/working/          ← 工程师 Agent 的工作记忆（私有）
│   └── "auth.py 第 15 行需要改..."
└── /agent/reviewer/working/          ← 审查 Agent 的工作记忆（私有）
    └── "发现 3 个问题，2 个已修复..."
```

**关键机制**：
- **MemoryScope**：作用域内可读写，外不可见
- **MemorySlice**：跨作用域只读视图（Coordinator 用这个给 Worker 看"你需要的上下文"）
- **复合评分检索**：`score = (语义相似度 × 0.5) + (时间衰减 × 0.3) + (重要性 × 0.2)`
- **LLM 自动推断**：新记忆该放哪个 scope，该合并还是新增

**对 AgentHub 的启发**：这是最直接的参考模式。你不需要自己发明作用域——它天然映射到群聊：
- 群聊决策 = `/group/decisions/`
- Coordinator 输出 = `/group/tasks/`
- 每个 Agent 的私有工作记忆 = `/agent/{name}/working/`

### 3.2 Cognee — Session 优先 + 图回退 ⭐⭐⭐⭐⭐

Cognee 是一个开源"记忆控制面"，17.5K stars。核心创新：**双层查询 + 自动路由**。

```
recall("JWT token 过期时间是多少？")
    │
    ├─→ 1. Session Memory (快速缓存，session_id 隔离)
    │     如果命中 → 返回（<10ms）
    │
    └─→ 2. Knowledge Graph (永久图，跨 session)
          自动选择检索策略: TEMPORAL / SEMANTIC / GRAPH / HYBRID
```

**对 AgentHub 的直接应用**：

```
用户追问: "JWT 过期时间能改成 7 天吗？"
    │
    ▼
1. Session Memory (Redis L1)
   → 命中：上次后端 Agent 的回复在滑动窗口内
   → 直接给后端 Agent 看相关片段
   → 不触发图查询

用户新需求: "博客系统怎么设计？"（跨 session）
    │
    ▼
1. Session Memory → 未命中（这是新话题）
    │
2. Knowledge Graph (PG 表)
   → ENTITY: 博客系统
   → 关联: [前端专家 → React 经验, 后端专家 → FastAPI 经验]
   → 检索到: 上一次做"文章系统"的任务产物
```

**对 AgentHub 的启发**：Redis L1 做 Session Memory，PG + 简单文件做 Knowledge Graph。不需要引入 pgvector。用 `agents` 表的能力标签、`tasks` 表的完成记录、文件系统的产物文件就够了。

### 3.3 Letta (MemGPT) — 三层记忆 + Agent 自主管理 ⭐⭐⭐⭐⭐

Letta 把记忆像 OS 一样分层：

```
┌─────────────────────────────────────────────┐
│  Core Memory (RAM)                          │
│  永远在 context window 里                    │
│  Agent 自己读写                              │
│  存: 当前任务定义、关键决策、活跃约束         │
│  容量: ~2K tokens                           │
├─────────────────────────────────────────────┤
│  Recall Memory (Disk Cache)                  │
│  可搜索的对话历史，不在 context 里            │
│  Agent 通过工具调用搜索                       │
│  存: 完整聊天记录、代码上下文                 │
│  容量: 无限制                                │
├─────────────────────────────────────────────┤
│  Archival Memory (Cold Storage)              │
│  长期向量存储，Agent 通过工具调用检索          │
│  存: 跨项目的知识、过去的经验                 │
│  容量: 无限制                                │
└─────────────────────────────────────────────┘
```

**关键是 Agent 自己管理**：不是系统自动往外挤旧记忆，而是 Agent 在推理过程中自己决定"这个信息很重要，存到 Core Memory"。

**对 AgentHub 的映射**：

| Letta 层 | AgentHub 实现 | 内容 |
|---------|-------------|------|
| Core Memory | 注入到 system prompt 的工作台切片 | 当前任务 + 相关对话片段 + Agent 角色 + 用户偏好 |
| Recall Memory | Redis L1 滑动窗口 + PG messages 表 | 完整聊天记录 |
| Archival Memory | 文件系统 work_dir（CLAUDE.md, artifacts/） | 项目上下文、历史产物 |

### 3.4 bMAS — 黑板模式 ⭐⭐⭐⭐

学术论文（Han et al., Jul 2025）。架构极简但效果拔群：

```
┌──────────────────────────────────────┐
│            Blackboard                 │
│     (唯一的通信和记忆中心)             │
│                                       │
│  · 用户消息                           │
│  · Agent 回复                         │
│  · 任务状态                           │
│  · 当前上下文                         │
└────────────┬─────────────────────────┘
             │
    ┌────────┴────────┐
    ▼                 ▼
┌────────┐     ┌──────────┐
│ Meta   │────▶│ Planner  │  每轮动态选择
│ Agent  │────▶│ Critic   │  哪些 Agent
│ (控制) │────▶│ Decider  │  需要激活
└────────┘     │ Resolver │
               └──────────┘
```

**对 AgentHub 的启发**：你的 Coordinator 就是这个 Meta Agent。它读黑板（工作台），决定派谁上场。不需要每个 Agent 都看到全部上下文。

### 3.5 PSMAS — 阶段调度 ⭐⭐⭐⭐

论文发现（arXiv, 2025）：**调度（谁在什么时候说话）和压缩（每个人看到什么）是独立的优化维度。**

| 优化 | Token 节省 | 性能损失 |
|------|:---:|:---:|
| 只做调度（闲置 Agent 不注入上下文） | -18% | 0% |
| 只做压缩（压缩闲置 Agent 的上下文） | -9% | -1.2pp |
| **调度 + 压缩** | **-27%** | **-2.1pp** |

**对 AgentHub 的直接应用**：在一个"做登录页面"的任务中——

```
激活的 Agent（需要完整上下文）:
  · Coordinator → 看到用户需求 + Agent 能力表
  · 前端专家 → 看到 task-1 描述 + 上一次的代码规范偏好
  · 后端专家 → 看到 task-2 描述 + auth.py 上次的代码片段

闲置的 Agent（只需要压缩摘要）:
  · 代码审查员 → "当前在做登录页面，task-1(前端)和task-2(后端)进行中，完成后需要你审查"
  · 其他不相关的 Agent → 不推送
```

## 四、AgentHub 群聊工作台 — 推荐设计

### 4.1 不引入新基础设施

调研后的结论：**不需要 pgvector、Neo4j、Chroma、LanceDB。** 用已有设施就能做到。原因：
- Letta 团队实验证明：`grep + search_files` 文件系统工具 + GPT-4o mini 在 LoCoMo 基准上达到 74.0%，超过 Mem0 的专用图工具（68.5%）
- AgentHub 的会话量（Demo 级别）不需要图数据库的 scale

### 4.2 推荐：作用域树 + 三层访问 + 黑板协调

```
┌── Workspace Tree (PG agents/tasks/sessions + Redis L1 + 文件系统) ──┐
│                                                                       │
│  /group/{group_id}/                                                   │
│  ├── /decisions/          ← 群组决策记录 (PG session.summary)         │
│  │   ├── 2026-05-23: JWT 过期时间 24h→7d                             │
│  │   └── 2026-05-23: 选择 Tailwind CSS 做样式框架                    │
│  ├── /tasks/              ← 当前任务状态 (PG tasks 表)               │
│  │   ├── task-1: COMPLETED → 产物 auth.py                            │
│  │   └── task-2: RUNNING  → Worker 后端专家                           │
│  ├── /artifacts/          ← 产物索引 (文件系统)                       │
│  │   ├── auth.py → /tmp/agenthub/artifacts/task-1/                   │
│  │   └── LoginPage.tsx → /tmp/agenthub/artifacts/task-2/             │
│  ├── /members/            ← 成员名片 (PG agents 表)                   │
│  │   ├── 前端专家: {role, capabilities, model, workload, status}     │
│  │   ├── 后端专家: {...}                                              │
│  │   └── 代码审查员: {...}                                            │
│  └── /preferences/        ← 用户偏好 (PG session.settings)            │
│      ├── code_style: "Tailwind CSS + Airbnb 规范"                    │
│      └── framework: "React + FastAPI"                                │
│                                                                       │
│  /agent/{agent_id}/       ← 私有工作区 (CLI work_dir + Redis)         │
│  ├── /working/            ← Agent 当前工作记忆 (CLI 内部)             │
│  └── /learnings/          ← Agent 学到的经验 (文件系统)               │
│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

### 4.3 Coordinator 的工作流

```python
class WorkspaceCoordinator:
    """Coordinator 读完整 Workspace，按需裁剪注入给 Worker。"""

    async def dispatch(self, user_message: str, group_id: UUID):
        # 1. 构建工作台全景
        workspace = await self._build_workspace(group_id)
        #    workspace.chat_log    ← Redis L1 (最近 20 条)
        #    workspace.tasks       ← PG tasks 表 (当前任务状态)
        #    workspace.members     ← PG agents 表 (成员能力)
        #    workspace.artifacts   ← 文件系统 ls
        #    workspace.preferences ← PG session.settings

        # 2. Coordinator LLM 分解（拿到工作台全景）
        plan = await self.llm.decompose(user_message, workspace)

        # 3. 按需裁剪 → 注入给每个 Worker（不是全部）
        for task in plan.tasks:
            worker = task.assigned_worker

            # 裁剪：只给这个 Worker 相关的片段
            slice = workspace.slice_for(
                agent=worker,
                task=task,
                relevant_chat=self._find_relevant_messages(workspace.chat_log, task),
                relevant_artifacts=self._find_relevant_artifacts(workspace.artifacts, task),
            )
            await self._execute(task, worker, slice)

    def _find_relevant_messages(self, chat_log, task):
        """从 Redis L1 中搜索与当前任务相关的消息片段。"""
        keywords = task.get("keywords", [])
        return [m for m in chat_log
                if any(kw in str(m) for kw in keywords)]

    def _find_relevant_artifacts(self, artifacts, task):
        """从文件系统产物中找出相关文件。"""
        return [a for a in artifacts
                if task["intent"] in a.get("tags", [])]
```

### 4.4 记忆检索的复合评分

借鉴 CrewAI 的评分公式，AgentHub 的检索排序：

```python
def relevance_score(memory, query, now):
    """复合评分：语义 + 时间 + 重要性。"""
    semantic = cosine_similarity(memory.embedding, query.embedding)  # 0-1
    recency = math.exp(-(now - memory.timestamp).days / 7)          # 指数衰减，半衰 7 天
    importance = memory.importance                                  # 0-1，LLM 推断或手动

    return semantic * 0.5 + recency * 0.3 + importance * 0.2
```

对 AgentHub 来说，初期不需要 embedding。用关键词匹配替代 semantic，用消息 seq 替代 recency，用 Pin 状态替代 importance：

```python
# 简化版（不需要向量库）
def simple_score(message, query_keywords):
    keyword_match = sum(1 for kw in query_keywords if kw in str(message)) / len(query_keywords)
    recency = message.seq / max_seq  # 越新越高
    is_pinned = 1.0 if message.pinned else 0.0
    return keyword_match * 0.5 + recency * 0.3 + is_pinned * 0.2
```

```sql
ALTER TABLE sessions ADD COLUMN preferences JSONB DEFAULT '{}';
ALTER TABLE sessions ADD COLUMN decisions JSONB DEFAULT '[]';
```

## 六、关键设计决策

### 6.1 文件系统作为记忆后端（推荐）

受 Letta 团队发现启发：`grep + 结构化 markdown 文件` 优于专用向量库。

AgentHub 的文件系统记忆布局：

```
/tmp/agenthub/
├── sessions/{agent_id}/
│   ├── CLAUDE.md              ← 项目上下文 + 记忆注入（已设计）
│   └── .claude/skills/        ← Skills 文件（已设计）
├── artifacts/{task_id}/
│   ├── source_files/          ← 生成的代码
│   └── diff/                  ← diff 预览
└── workspace/{group_id}/
    ├── decisions.md            ← 群组决策日志（markdown，人类可读）
    ├── task_board.md           ← 任务看板快照
    └── preferences.md          ← 用户偏好记录
```

好处：
- Agent（CLI 子进程）可以直接 `read`/`grep` 这些文件
- 不需要额外 API
- 人类可以直接打开看
- Letta 实验证明这比专用向量库效果好

### 6.2 阶段调度（重要但不急）

PSMAS 论文的核心发现：**只给激活的 Agent 注入完整上下文，闲置 Agent 给一句话摘要就够了。**

在 M3 实现时，Coordinator 的逻辑应该包含：

```python
# Coordinator 的调度决策
activated = [前端专家, 后端专家]   # 收到子任务
idle = [代码审查员, 其他Agent]      # 没收到子任务

for agent in activated:
    context = workspace.full_slice(agent, task)    # 完整上下文
for agent in idle:
    context = workspace.one_line_summary()          # "当前在做登录页面，完成后需要你审查"
```

### 6.3 Loop Guard（已验证的模式）

agentchattr 和 OpenClaw 都实现了：检测连续 N 条消息都是 Agent 发送且互相 @，强制静默 30 秒。

Harness 应该内置这个检测（之前 PRD v3 已纳入）。

## 七、总结：从"记忆存储"到"工作台管理"

| | 之前的设计思路 | 推荐的设计思路 |
|---|---|---|
| **定位** | L1-L4 存储层次 | Workspace + 按需裁剪 |
| **Coordinator 角色** | 分解任务 | 分解任务 + 管理上下文 + 裁剪注入 |
| **Agent 能看到什么** | 全部 L1 窗口 | Coordinator 裁剪的工作台切片 |
| **底层存储** | Redis/PG/文件/RAG | Redis + PG + 文件系统（无新引入） |
| **组织形式** | 按存储层级 | 按作用域树 |

**核心公式**：

```
高效群聊 = 黑板(Workspace) + 调度(Phase Scheduling) + 裁剪(Context Slice)
```

- **黑板**：所有信息集中在一个结构化工作台
- **调度**：只激活与当前任务相关的 Agent
- **裁剪**：每个 Agent 只看到自己需要的上下文片段

这三个模式分别来自 bMAS（黑板）、PSMAS（调度）、CrewAI（作用域裁剪），已被论文和开源项目验证。AgentHub 不需要引入新的基础设施就能落地。
