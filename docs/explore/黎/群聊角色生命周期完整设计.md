# 群聊角色生命周期 — 完整设计

> 2026-05-23 | 回答"群聊启动后每个角色怎么活怎么死，状态怎么流转"

---

## 零、先搞清楚有哪些角色

```
群聊中的 5 种角色：

1. 用户 (Human)        — 发消息的人，永远在线，浏览器开着
2. Coordinator        — 任务分解器，SDK 模式，按需调用，无子进程
3. Worker Agent       — 干活的 Agent，CLI 子进程，spawn → 执行 → terminate
4. ChatService        — 消息总线和路由，FastAPI 进程内常驻
5. ActivationManager  — 进程生命周期管理，ChatService 内部组件
```

## 一、完整时间线（从群创建到任务完成）

```
时间轴 ──────────────────────────────────────────────────────────────────▶

Phase 0: 群创建         Phase 1: 等待中        Phase 2: 任务执行         Phase 3: 回到等待
                          
User 创建群             用户随时可能发消息       Coordinator 分解          所有子进程已退出
GroupService.create()   只有 WS 连接活跃         ActivationMgr spawn      Workspace 已更新
生成 Coordinator 配置   无任何子进程              Workers 流式输出         Coordinator 待命

─────┼───────────────────┼──────────────────────┼────────────────────────┼─────▶

    创建群                 第一条消息              最后一条消息回复完
    POST /api/groups      WS send_message        所有进程 terminate
```

## 二、每个角色的完整生命周期

### 2.1 Coordinator（轻量，SDK 模式）

```
状态机：IDLE → THINKING → DISPATCHING → IDLE

   ┌──────────────────────────────────────────────────────┐
   │                                                      │
   ▼                                                      │
 [IDLE] ──用户发任务消息──▶ [THINKING] ──产出 plan──▶ [DISPATCHING] ──spawn完──▶ [IDLE]
   │                            │                         │
   │ 等待中                      │ LLM 调用中               │ 逐个 spawn Worker
   │ 无子进程                    │ ~2-5秒                  │ 写入 tasks 表
   │                            │                         │ 发布 TaskPlan 事件→WS
   └────────────────────────────┘                         └──────────────────────┘
```

**关键设计决定**：Coordinator 不是持久进程，不是 `is_system=True` 的 Agent，而是一个 SDK 函数调用。

对比原 spec：
- **原 spec（S5）**：创建群组时生成一个 Coordinator Agent（`is_system=True`），作为群成员可见，有独立的 provider/model/api_key
- **现在**：Coordinator 是 `CoordinatorService` 里的一个方法，用系统配置的默认 LLM（便宜模型如 Haiku），不占用 agents 表，不在群成员列表里显示

**为什么改**：
- Coordinator 只做分解，不需要完整工具生态（不读写文件、不跑 bash）
- SDK 调用比 spawn 子进程轻 100 倍
- 不需要维护 Coordinator 的"会话状态"——每次分解是独立调用
- 原 spec 的设计把 Coordinator 当成一个"特殊的 Worker"，但它其实是一个"路由器"

**但如果需要更智能的 Coordinator**（比如它能记住历史分解模式，越分解越准），可以改成这样：

```python
# 过渡方案：Coordinator 用 SDK，但调用时传入历史分解记录
plan = await coordinator.decompose(
    message=user_message,
    workspace=workspace,  # 包含之前的 task_board、decisions
)
# workspace.decisions 里已经有"上次登录系统分了 3 个子任务"这样的记录
```

### 2.2 Worker Agent（重量，CLI 子进程）

```
状态机：SLEEPING → SPAWNING → RUNNING → TERMINATING → SLEEPING
                            │  ↓
                            │ FAILED → RETRY_QUEUED → SPAWNING
                            │
                            └ AWAITING_APPROVAL → RUNNING / CANCELLED

   ┌────────────────────────────────────────────────────────────┐
   │                                                            │
   ▼                                                            │
[SLEEPING] ──Coordinator分配任务──▶ [SPAWNING] ──子进程启动──▶ [RUNNING]
   │                                    │                        │
   │ 无进程                             │ asyncio.create_         │ 流式输出 token
   │ 状态存在 JSONL 文件                 │   subprocess_exec()    │ → ChatService
   │ 内存占用: 0                        │ ~1-2 秒                │ → WS → 前端
   │                                    │                        │
   │                                    │                        ├─ 正常完成 → [TERMINATING]
   │                                    │                        ├─ 危险操作 → [AWAITING_APPROVAL]
   │                                    │                        └─ 崩溃 → [FAILED]
   │                                    │                                    │
   │                                    │                                    │
   │  ◀─────────────────────────────────────────────────────────────────────┘
   │
   │  [TERMINATING]
   │    · 进程退出
   │    · 状态写入 JSONL: ~/.claude/sessions/{agent_id}.jsonl
   │    · 产物写入: /tmp/agenthub/artifacts/{task_id}/
   │    · 更新 PG tasks 表: status=COMPLETED
   │    · 更新 Workspace.task_board
   │    · 发布 StreamingCompleted → WS
   │    → [SLEEPING]
   │
   │  [AWAITING_APPROVAL]
   │    · 进程暂停（不退出！checkpoint 还在内存里）
   │    · 发布 ApprovalRequested → WS → 用户看审批卡片
   │    · 用户 APPROVE → [RUNNING]（进程继续）
   │    · 用户 REJECT → [TERMINATING]（发 SIGTERM，task=CANCELLED）
   │    · 超时 5min → [TERMINATING]（自动拒绝）
   │
   │  [FAILED]
   │    · retry_count < 3 → [RETRY_QUEUED] → [SPAWNING]（重新 spawn）
   │    · retry_count >= 3 → [TERMINATING]（task=FAILED，通知 Coordinator）
   │
   └────────────────────────────────────────────────────────────┘
```

**对比原 spec**：
- **原 spec（S14）**：Worker 通过 Celery Worker Pool 拉取任务，Harness 做 BudgetController 校验，Worker 调用 LLMAdapter
- **现在**：Worker = CLI 子进程，Harness 只做前置校验（环检测+路由），Budget 交给 CLI 内部（`--max-turns`），执行就是 spawn + 等退出

**为什么 CLI 子进程替代 Celery Worker**：
- Celery Worker 需要自己实现工具系统（9 个 BaseTool → 55+ CLI 工具），工程量差 6 倍
- CLI 子进程自带完整的工具生态、权限、预算控制
- asyncio.create_subprocess_exec 替代 Celery Canvas，无 RabbitMQ 依赖

### 2.3 User（人类，浏览器）

```
用户状态不是系统管理的，但用户行为触发状态流转：

操作                触发什么
──────────────────────────────────────────
打开群聊页面         WS 连接，拉取 session 历史消息
发送消息             WS frame → ChatService → 意图检测
  ├─ 闲聊           Coordinator 不触发，如果有 @Agent 则直接路由
  ├─ @Agent         直接路由到目标 Agent（spawn 该 Agent 的 CLI）
  └─ 任务消息       Coordinator 分解 → 批量 spawn
审批操作             POST /api/approvals/{task_id}/approve|reject
  ├─ APPROVE        ActivationManager 发信号让暂停的进程继续
  └─ REJECT         发 SIGTERM，task=CANCELLED
Pin 消息             POST /api/messages/{id}/pin → 更新 session 长期上下文
查看产物             打开 Diff/Preview 卡片
创建 Agent           卡片式表单 → AgentService.create()
创建群组             选成员 → GroupService.create() → 自动生成 Coordinator 配置
```

### 2.4 ActivationManager（进程生命周期管理）

```
这是 ChatService 的内部组件，不是独立服务。

职责：
  1. 跟踪当前活跃的子进程: active_processes: dict[agent_id → Process]
  2. 按需 spawn: 只在 Coordinator 分配任务时启动
  3. 支持 --resume: 如果该 Agent 之前有过 session，从 JSONL 恢复上下文
  4. 数量限制: 最多同时 N 个子进程（默认 5，可配）
  5. 超时 kill: 单个任务最长 10 分钟，超时发 SIGTERM
  6. cleanup: 进程退出后清理临时文件，更新 task 状态

接口：
  async def spawn(agent, task, context_slice) → Process
  async def resume_or_spawn(agent, task, context_slice) → Process
  async def wait_all(processes) → list[TaskResult]
  async def kill(agent_id) → None
  def active_count() → int

对比原 spec：
  原: Celery Worker Pool + apply_async() + Canvas chord/group/chain
  现: asyncio.create_subprocess_exec + asyncio.gather + 手动管理依赖顺序
```

## 四、与原始 spec 的关键差异对照表

| | 原 spec (v2.1) | 现在 (v3/v4) | 为什么改 |
|---|---|---|---|
| **Coordinator 形态** | `is_system=True` 的 Agent，在群成员列表可见 | SDK 函数调用，不在成员列表 | Coordinator 不需要完整工具，SDK 够用且更轻 |
| **Coordinator 模型** | 和 Worker 一样配 provider/model | 系统默认，用便宜模型（如 Haiku） | 分解不是重体力活，不需要旗舰模型 |
| **任务调度** | Celery Canvas (chord/group/chain) | asyncio.gather + 手动依赖排序 | Demo 不需要独立队列服务，asyncio 够用 |
| **Worker 执行** | Celery Worker + LLMAdapter.stream() | CLI 子进程 spawn + stdout pipe | CLI 自带 55+ 工具，不需要自建 9 个 BaseTool |
| **事件溯源** | task_events 表记录每一次状态变更 | task.status 字段直接更新 | Demo 中审计/重放不可见，省一张表 |
| **Worker 状态持久化** | 无（Celery 任务无状态） | JSONL 文件（CLI 自动写） | --resume 恢复上下文，用户追问无需重传全部历史 |
| **审批时进程状态** | task.state → AWAITING_APPROVAL（进程可能继续/重试） | 进程暂停不退出，checkpoint 在内存 | 更简单：等用户决定后继续或 kill |
| **记忆注入** | 每次调用都注入完整 L1 窗口 | 首次 session 创建时注入一次，后续靠 --resume | CLI 自己管理对话内状态，不重复注入 |
| **闲置 Agent** | 始终在线 (status=online) | 进程退出 (SLEEPING) | 不占用内存，需要时 spawn |
| **群聊成员列表中的 Coordinator** | 可见（蓝色系统标识） | 不可见（内部服务） | 减少 UI 复杂度，用户不需要感知路由器 |

## 五、需要确认的边界问题

有几个设计点还比较模糊，需要你拍板：

**Q1: Coordinator 的分解记录要不要存？**
- A: 不存 → 每次分解是独立调用（简单）
- B: 存 decisions 表 → Coordinator 能看到"上次类似任务怎么分解的"（更智能，但需要额外字段）
- 建议: M2-M3 用 A，M4 有时间就加 B

**Q2: Worker 的 --resume 策略**
- A: 每次都 --resume（从 JSONL 恢复上次完整上下文）→ Agent 记得所有历史
- B: 只在追问/修改场景 --resume，新任务从头开始 → 上下文更干净
- 建议: B。新任务不需要上次的代码细节，追问/修改才需要

**Q3: 审批时进程暂停 vs 退出重来**
- A: 暂停（进程活着，checkpoint 在内存）→ 恢复快，但占内存
- B: 退出，用户 APPROVE 后重新 spawn → 不占内存，但恢复慢
- 建议: A。审批通常在几秒-几分钟内决定，占几百 MB 可接受

**Q4: 多个用户同时在一个群里发任务？**
- Demo 不需要支持，但架构上：第二个消息应该排队，等第一个任务的 Coordinator 返回后再处理
- 建议: ChatService 里加一个 per-session 的锁，同一时间只处理一条任务消息

**Q5: Worker 失败后要不要通知用户？**
- 原 spec 没有这个设计
- 建议: FAILED + retry_count=3 → WS 推送错误卡片："{Agent名} 执行失败（已重试 3 次），请检查需求或手动重试"

## 六、用伪代码串一遍完整流程

```python
# ── Phase 0: 群聊创建 ──
async def create_group(name, member_ids):
    group = Group(name=name)
    group.coordinator_config = {
        "model": "claude-haiku-4-5",  # 便宜模型
        "provider": "anthropic",
    }
    # 注意：不再创建 Coordinator Agent 实体
    await db.save(group)
    await db.add_members(group.id, member_ids)
    return group

# ── Phase 1-2: 用户发消息 → 意图检测 → 路由 ──
async def on_user_message(session_id, content, mentions):
    msg = Message(role="user", content=content, mentions=mentions)
    await db.save(msg)
    await l1.append(session_id, {"role": "user", "content": content})

    # 意图检测
    if mentions:
        # 有 @ → 直接路由
        return await route_to_agent(mentions, content, session_id)
    elif is_task_intent(content):
        # 任务意图 → Coordinator 分解
        return await coordinator_flow(session_id, content)
    else:
        # 闲聊 → 不做任何事，消息仅展示
        return None

# ── Phase 2: Coordinator 分解 + Worker 执行 ──
async def coordinator_flow(session_id, content):
    workspace = await build_workspace(session_id)
    # workspace: {chat_log, tasks, members, artifacts, preferences}

    # Coordinator LLM 调用（SDK 模式，轻量）
    plan = await coordinator_sdk.decompose(
        message=content,
        workspace=workspace,
    )

    # Harness 校验
    harness.validate(plan)            # 环检测
    harness.route_workers(plan, workspace.members)  # 能力匹配 + 负载检查

    # 写入 tasks 表
    parent_task = await db.create_task(plan)
    await ws.broadcast(session_id, TaskPlanCard(plan))

    # 分批执行
    results = []
    # 第一批：无依赖的并行执行
    roots = [t for t in plan.tasks if not t.depends_on]
    procs = []
    for task in roots:
        agent = workspace.members[task.assigned_worker]
        context_slice = workspace.slice_for(agent, task)
        proc = await activation_mgr.spawn(agent, task, context_slice)
        procs.append(proc)

    # 等待第一批全部完成
    for proc in procs:
        result = await proc.wait()
        results.append(result)
        await ws.broadcast(session_id, StreamCompleted(result))

    # 第二批：依赖已满足的
    dependents = [t for t in plan.tasks if t.depends_on]
    for task in dependents:
        if all_deps_completed(task, results):
            agent = workspace.members[task.assigned_worker]
            proc = await activation_mgr.spawn(agent, task, workspace.slice_for(agent, task))
            result = await proc.wait()
            results.append(result)

    # 更新 Workspace
    await update_workspace(session_id, results)
    await ws.broadcast(session_id, AllTasksCompleted(results))

# ── Phase 3: 回到等待 ──
# 所有子进程已退出，Workspace 已更新
# Coordinator 待命，等待下一条用户消息
```

## 七、总结

**核心变化**：从"常驻服务"变成"按需调度的短暂进程"。

```
原设计:  所有 Agent 在线 → Coordinator 是特殊 Agent → Celery 队列 → Worker 池拉取
新设计:  只有 Coordinator 逻辑在线 → 按需 spawn CLI → asyncio.gather → 进程退出
                                         ↑
                                    SDK 调用，不是 Agent
```

**三句说清**：
1. Coordinator 是路由器（SDK 调用，不占进程），Worker 是短暂工（CLI spawn → 干活 → 退出）
2. 激活不是预启动，是按 Coordinator 的 DAG 分批 spawn，干完活就 terminate，状态留在 JSONL 文件里
3. 和原 spec 最大的区别：Coordinator 从"群里的一个特殊 Agent"降级为"ChatService 里的一个 SDK 调用"，Celery 从"任务队列"降级为"asyncio.gather"
