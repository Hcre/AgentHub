  异常分支：T6' — C 首次 spawn 失败

  把主时间线 T6 换成异常路径：

  Pool.get_or_spawn(key_C, system_prompt=...)
    → spawn 后 100ms 内 proc.returncode = 1, stderr="auth error"
    → Pool 检测到失败，抛出 ClaudeRuntimeError("spawn 失败")
    ↓
  DiscussionOrchestrator catch 异常
    - **关键决策**：是否推进 C.wm？

  正确策略：不推进 watermark。原因：
  - C 还没看到任何消息，没产生发言
  - 下次 C 被选中时，重新 spawn + 重新计算 delta（应包含 m1..m4 全部）
  - 否则 wm 推进了但 CLI 没记录，C 永远丢失这些消息

  DiscussionOrchestrator:
    - m5_err = Message(content="（小李未响应）", sender=C, status=FAILED)
    - 不更新 C.wm
    - 继续下一轮（或者重新选择发言者）

  T8 重试：用户发新消息 m6，DiscussionOrchestrator 再次选 C：
  delta = WatermarkStore.get_delta(s1, C) → [m1, m2, m3, m4, m6]（仍是首次）
  trigger_text = 完整历史 + 新消息 + "[轮到你发言]"
  Pool.get_or_spawn(key_C, ...) → 这次 spawn 成功
  正常推送 + 回复

  新发现：watermark 必须有「成功提交」语义，不能在 spawn 时就推进，只能在
  read_until_result 成功完成后才推进。当前 proposal v3 没有明确这一点。

  ---
  反演四个根因

  根因: 1. 身份窒息
  T8 时刻（最严苛场景：A 复用 + 别人说了很多话）: system_prompt 永远 200 字符级；A
    看到 turn1 assistant 自己说过"喵～"形成稳定锚定；turn2 user 中的 delta
    即使长，但有明确"轮到你发言"边界
  改善程度: 显著改善
  ────────────────────────────────────────
  根因: 2. 协调者泄漏
  T8 时刻（最严苛场景：A 复用 + 别人说了很多话）: members_block 永远不含 D
  改善程度: 解决
  ────────────────────────────────────────
  根因: 3. 默认 persona 弱
  T8 时刻（最严苛场景：A 复用 + 别人说了很多话）: A.system_prompt 为空时用 P0 模板
  改善程度: 缓解
  ────────────────────────────────────────
  根因: 4. 口吻传染
  T8 时刻（最严苛场景：A 复用 + 别人说了很多话）: T4 B 看到「喵娘:
    喵～...」可能被诱导；T8 A 看到的 delta 不含别人的喵～（B/C 都不是猫娘风格）
  改善程度: 场景相关：当真有人模仿喵～后，才会污染下一个 Agent。需要独立工单

  ---
  推理暴露的新设计要求（必须补进 proposal v3）

  N1：Watermark 必须有 commit 语义

  问题：CLI spawn 成功 ≠ 发言成功。spawn 后失败 / read 超时 / Agent
  输出错误，都应保留 watermark 不动。

  对策：
  async def _stream_one(target, trigger):
      delta = wm_store.get_delta(...)
      try:
          async for evt in adapter.stream(request):
              yield evt
          # 只有完整收到 result 才推进 wm
          wm_store.update(s1, target, latest_delta_msg_id)
      except (RuntimeError, BrokenPipeError, TimeoutError):
          # 不更新 wm，下次重试
          ...

  N2：Pool 重 spawn 的语义边界

  问题：proc_A 在 T8 之前已崩溃，T8 调 get_or_spawn(key_A, ...) 应该做什么？
  - 选项 A：检测到崩溃 → 重 spawn → 但 CLI 内部历史丢失（A
  不再记得自己说过"喵～"）→ 长驻收益归零
  - 选项 B：检测到崩溃 → 重 spawn + 主动用 --resume <key_A> → CLI 从 disk session
  恢复历史 → 但需测试 --resume 与 --input-format stream-json 是否兼容

  待补 Phase 0.5 V5：测试 --resume <key> --input-format stream-json
  是否能恢复历史。如果可以，崩溃恢复方案明确；否则需要"补灌历史"机制。

  N3：trigger_text 的「轮到你发言」标记可能引发误读

  问题：A 在 T2 看到 "用户: 做一次支付功能评审\n\n[轮到你发言]"。LLM 是否会把
  [轮到你发言] 当作用户原话的一部分？
  - 风险：A 可能回复 "轮到我了喵～..." 之类的复读
  - 待办：实测时关注前 5 次回复是否出现复读 [轮到你发言]，必要时改用 system
  reminder 形式

  N4：用户中途插话不广播但延迟感知

  问题：T5 用户插话 m4，但 B 已经发言完成（wm=m3），如果协调者下一轮选了 A，A
  会看到 m3 + m4。但B 永远看不到 m4，除非协调者再选 B 发言。
  - 这是 pull 模式的固有特性，不是 bug
  - 但需要文档明确：沉默 Agent 不感知群里变化，直到下次被触发
