# 记忆系统设计：Q&A 记录

> 本文档记录关于记忆系统的所有问答，涵盖技术选型、边界划分、性能优化等核心问题。

---

## 一、基础认知问题

### Q1: cc-haha 是否对记忆有相关处理？还是全权交给 CLI？

**A:**
cc-haha 对记忆有完整的自主处理机制，并非全权交给 CLI。

| 记忆类型 | 存储位置 | 作用范围 |
|---------|---------|---------|
| **Auto-memory** | `~/.claude/auto-memory/` | 全局 |
| **Agent-memory** | `~/.claude/agent-memory/<agent>/` | Agent 级别 |
| **Team-memory** | `~/.claude/auto-memory/team/` | 团队共享 |
| **Session-memory** | `~/.claude/session-memory/` | 单次会话 |

**核心机制**：cc-haha 构建了一套完整的**文件型记忆系统**，通过 `loadMemoryPrompt()` 将记忆注入到 CLI 的 System Prompt 中。

---

### Q2: HanaAgent (openhanako) 是否依赖 CLI 的记忆处理？

**A:**
HanaAgent 的记忆系统**完全独立于任何外部组件**。

- HanaAgent 使用 **Pi SDK** 作为底层运行时（非 Claude CLI）
- 记忆系统与 Pi SDK **完全解耦**
- 不需要处理任何记忆边界问题

**这与依赖 Claude CLI 的项目有本质区别**。

---

### Q3: 依赖 CLI 的项目需要处理记忆边界吗？

**A:**
**是的，必须明确处理记忆边界。**

```
┌─────────────────────────────────────────────────────────────┐
│                    项目 (IM 层)                             │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────┐ │
│  │  人格/身份   │  │  技能/Skill │  │  长期知识/FactStore │ │
│  └─────────────┘  └─────────────┘  └─────────────────────┘ │
│                         ↑                                    │
│                    通过 System Prompt 注入                    │
└────────────────────────────│────────────────────────────────┘

                    │  Claude CLI    │
                    │  (子进程)       │
                    │  ┌───────────┐ │
                    │  │会话历史    │ │
                    │  └───────────┘ │
                    └───────────────┘
```

## 二、记忆选择机制

### Q4: 什么叫"对话前 AI 选择相关记忆"？

**A:**
cc-haha 在每次对话前调用 `findRelevantMemories()`，使用 Sonnet 模型智能选择相关记忆。

**流程：**
```
用户输入: "帮我优化接口"
     │
     ▼
┌─────────────────────────────────────────────────────┐
│  1. 扫描所有记忆文件（只读 frontmatter）             │
│     └── user_profile.md, tech_stack.md, ...        │
│                                                     │
│  2. 构建 manifest（轻量摘要）                       │
│     └── - [user] profile.md: 后端开发              │
│         - [tech] stack.md: Spring Boot...          │
│                                                     │
│  3. AI (Sonnet) 选择相关记忆                       │
│     └── 选中: tech_stack.md, recent_work.md       │
│                                                     │
│  4. 注入选中的记忆到 System Prompt                  │
└─────────────────────────────────────────────────────┘
```

**核心价值**：不是把所有记忆都塞进去，而是让 AI 帮你找到"这个场景最需要哪些记忆"。

---

### Q5: 记忆选择 AI 是每个对话独立吗？还是全局唯一？

**A:**
**每次对话独立调用，使用全局固定模型（Sonnet）**

```
┌────────────────────────────────────────────────────────────┐
│                    模型选择策略                             │
├────────────────────────────────────────────────────────────┤
│                                                             │
│  记忆选择 AI: 固定使用 Sonnet 模型                         │
│  ├── 不是全局唯一实例                                       │
│  ├── 每次对话独立 API 调用                                   │
│  └── 优点：成本低、速度快                                   │
│                                                             │
│  主任务 AI: 用户选择的模型 (Claude/GPT/DeepSeek 等)       │
│  ├── 每个会话可以不同                                       │
│  └── 负责执行实际任务                                       │
│                                                             │
└────────────────────────────────────────────────────────────┘
```

**为什么不用全局唯一实例？**
1. 不需要共享状态：每次选择都是独立的
2. 简化实现：不用管理实例生命周期
3. 成本低：Sonnet 调用非常便宜
4. 可靠性高：一个实例崩了不影响所有对话

---

### Q6: 什么叫扫描所有记忆文件？是将记忆文件全量塞入吗？

**A:**
**不是塞入全部内容，只读取 frontmatter（前 30 行）**

```
┌─────────────────────────────────────────────────────────────────┐
│                    扫描记忆文件流程                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 文件系统扫描（代码层面，不是 AI 调用）                        │
│     └── readdir() 遍历目录，找到所有 .md 文件                    │
│                                                                 │
│  2. 只读取 frontmatter（前 30 行）                              │
│     ├── 不读取完整文件内容                                      │
│     ├── 提取：description、type                                 │
│     └── 性能：减少 90%+ 的 IO                                   │
│                                                                 │
│  3. 构建轻量 manifest（文本列表）                               │
│     └── 传给 AI 的不是文件内容，而是"描述列表"                   │
│                                                                 │
│  4. AI 根据描述选择                                             │
│     └── AI 只看到：文件名 + description + 类型                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**对比：两种方案的 token 消耗**

| 方案 | 每次调用 token | 记忆文件总大小 |
|------|---------------|---------------|
| **塞入全部内容** | 100KB+ | 10MB |
| **cc-haha 方式** | ~2KB | 10MB |
| **节省** | 98%+ | 相同 |

---

### Q7: 性能怎么样？每次对话多一次 AI 调用会不会让用户等待时间变长很大？

**A:**
**增加很小，用户几乎感知不到**

| 阶段 | 耗时 | 占比 |
|------|------|------|
| 扫描 frontmatter | 5-20ms | <1% |
| Sonnet API 调用 | 300-800ms | 1-5% |
| **记忆选择总计** | **~500ms** | **~3%** |
| 主任务执行 | 10-30秒 | 97% |

**优化手段：**
```typescript
// 1. 并行读取
const headerResults = await Promise.allSettled(...)

// 2. 限制文件数量
const MAX_MEMORY_FILES = 200

// 3. 只读前 30 行
const FRONTMATTER_MAX_LINES = 30

// 4. 最小化 token
max_tokens: 256
```

**结论：**
- 500ms vs 30秒 = 1.7% 额外延迟
- 可以并行执行，不阻塞主流程
- **先跑起来，发现瓶颈再优化**

## 三、防重复机制

### Q8: 每次对话都要扫描一次记忆吗？10 次对话扫描 10 次记忆？

**A:**
**不是！有完善的防重复机制**

cc-haha 使用 `alreadySurfaced` 机制防止重复选择：

```typescript
// findRelevantMemories.ts
export async function findRelevantMemories(
  query: string,
  memoryDir: string,
  signal: AbortSignal,
  recentTools: readonly string[] = [],
  alreadySurfaced: ReadonlySet<string> = new Set(),  // ← 关键参数
): Promise<RelevantMemory[]> {
  // 过滤掉之前已经选过的记忆
  const memories = (await scanMemoryFiles(memoryDir, signal)).filter(
    m => !alreadySurfaced.has(m.filePath),  // ← 跳过已选过的
  )
  // ...
}
```

**10 次对话的实际流程：**

```
对话 1: 选中 tech_stack.md, recent_work.md
        → alreadySurfaced = { tech_stack, recent_work }

对话 2: 扫描时跳过已选 → 只剩 user_profile 等
        → 选中 caching_guide.md
        → alreadySurfaced = { tech_stack, recent_work, caching_guide }

...以此类推
```

**其他防重复机制：**

| 机制 | 说明 |
|------|------|
| **MAX_MEMORY_BYTES** | 限制总 token 大小，超出不再选择 |
| **FileStateCache** | 过滤掉用户已读取过的文件 |
| **最近使用的工具** | 不重复选择工具文档 |
| **限制数量** | `.slice(0, 5)` 最多选 5 个 |

## 四、与 CLI 的边界划分

### Q9: cc-haha 和 CLI 的记忆边界在哪里？

**A:**
**边界清晰，各管各的**

```
┌─────────────────────────────────────────────────────────────────┐
│                    cc-haha (IM 层)                              │
│  ┌───────────────────────────────────────────────────────────┐ │
│  │ 记忆文件（auto-memory/）                                   │ │
│  │ ├── MEMORY.md (索引)                                       │ │
│  │ ├── user_profile.md                                        │ │
│  │ ├── tech_stack.md                                          │ │
│  │ └── ...                                                    │ │
│  └───────────────────────────────────────────────────────────┘ │
│                           │                                    │
│                    注入 System Prompt                          │
└───────────────────────────┼─────────────────────────────────────┘
                            │
┌───────────────────────────▼───────────────────────────────────┐
│                    Claude CLI (会话层)                         │
│  ┌───────────────────────────────────────────────────────────┐ │
│  │ 会话历史 (session-id)                                     │ │
│  │ ├── 对话 1: 用户问了什么，AI 回答了什么                   │ │
│  │ ├── 对话 2: 用户追问了什么，AI 继续回答                   │ │
│  │ └── auto-compact 压缩后的摘要                             │ │
│  └───────────────────────────────────────────────────────────┘ │
│                           │                                    │
│  CLI 自己维护会话历史，cc-haha 不干预                          │
└─────────────────────────────────────────────────────────────────┘
```

| 记忆类型 | 谁管理 | 如何注入 |
|---------|--------|---------|
| **项目知识** | IM 层 | System Prompt |
| **用户偏好** | IM 层 | System Prompt |
| **当前会话历史** | CLI | CLI 内部 |
| **会话摘要/压缩** | CLI 主导 | cc-haha 可协作 |

## 五、记忆存储结构

### Q10: 记忆应该用什么结构存储？

**A:**
参考 cc-haha 的设计：

**目录结构：**
```
memory/
├── meta/
│   └── manifest.json        # 记忆索引（快速检索）
├── user/
│   ├── profile.md           # 用户身份
│   ├── preferences.md       # 偏好设置
│   └── working_mode.md      # 工作模式
├── project/
│   ├── context.md           # 项目背景
│   ├── tech_stack.md        # 技术栈
│   ├── architecture.md      # 架构设计
│   └── coding_style.md      # 编码规范
├── session/
│   └── recent_work.md       # 最近工作进展
└── knowledge/
    ├── domain_knowledge.md  # 领域知识
    └── glossary.md          # 术语表
```

**manifest.json（记忆索引）：**
```json
{
  "version": "1.0",
  "memories": [
    {
      "id": "profile-001",
      "name": "用户身份",
      "path": "user/profile.md",
      "tags": ["identity", "profile"],
      "summary": "后端开发工程师，5年Java经验"
    }
  ]
}
```

**记忆文件格式（带 frontmatter）：**
```markdown
---
id: profile-001
name: 用户身份
tags: [identity, backend]
auto_sync: true
---

# 用户身份

## 基本信息
- 姓名：张三
- 职位：高级后端开发工程师
- 工作年限：5年
```

## 六、总结

### 核心要点

| 问题 | 答案 |
|------|------|
| cc-haha 记忆全权交给 CLI 吗？ | ❌ 否，有完整的自主处理 |
| 每次对话都选相同记忆吗？ | ❌ 有 `alreadySurfaced` 防重 |
| 扫描是全量读取吗？ | ❌ 只读 frontmatter，省 90%+ |
| 性能影响大吗？ | ❌ 约 500ms，占比 3% |
| IM 和 CLI 边界清晰吗？ | ✅ 各管各的，互不干扰 |
| 可以支持多会话不同模型吗？ | ✅ 可以，每个会话独立配置 |

### 建议借鉴的机制

| 机制 | 优先级 | 难度 |
|------|--------|------|
| 记忆索引文件结构 | ⭐⭐⭐ 高 | 简单 |
| 智能记忆检索 | ⭐⭐⭐ 高 | 中等 |
| 记忆作用域隔离 | ⭐⭐ 中 | 简单 |
| frontmatter 标记 | ⭐⭐ 中 | 简单 |
| 防重复选择机制 | ⭐⭐⭐ 高 | 中等 |
| 异步编译时机 | ⭐ 低 | 较复杂 |
