# 为什么简化——决策转变的推理链

> 日期：2026-06-08
> 记录从步 2 spec v1 → v2 → 架构总览 → 最终简化方案 的完整推理过程

---

## 起点：发现步 2 spec v1 有问题

审查 `coordinator-v3-step2-unified-loop-spec.md`（2026-06-07 版）时发现了三类问题：

1. **标题夸大**：声称「统一两个循环」，实际只动讨论态，任务执行循环一行不改
2. **执行态路由缺一块**：design v3 §4 画了 chitchat/progress/answer/modify 四条路径，代码只实现了两条（control + 简化 feed），闲聊被 `enqueue_note` 吞掉
3. **并发 streaming 标为正确行为**：两个 `_handle_group` 同时向同个 WebSocket 推事件，不是正确行为

修了这些，写出 v2。但 v2 还在 PAUSED/ask/resume 的框架内修修补补。

---

## 转折点 1：用户指出「你怎么看？」的 case

> 小美问了「用 Markdown 还是 CMS？」，用户回「你怎么看？」——这条消息该给谁？

我最初的回答是：`decide` 判断这不是答案 → `respond(后端阿强)`。

**用户纠正**：「你怎么看？」是在跟小美对话，应该 feed 给小美。小美的 CLI session 保留完整上下文，完全能处理反问。

这个纠正暴露了一个更深的问题：**Planner 不该判断「是不是答案」**。它该判断的是「这条消息在跟谁对话」。对话连续性的判断比答案匹配更可靠、更通用。

紧接着引出了第二个问题：小美想回复的话，有没有工具？

---

## 转折点 2：用户说「为什么要加 answer tool？她不能正常说话吗」

我想给小美加一个 `say` tool 让她能在干活时回复。**用户反问**：为什么要新工具？群组 agent 不是已经能正常说话了吗？

对——对话路径的 `_stream_one_agent` 输出直接推 WebSocket 进群聊。是执行路径的 `executor._consume` 把 worker 的文本吞了，然后开了 `ask` tool 作为结构化逃生口。**不是 worker 不能说话，是我把她的嘴堵上了又开了个洞。**

---

## 转折点 3：用户说「对话也是一种任务，任务也是一种对话」

> 任务时就进入了一种模式，完全不能进行对话。对话是一种特殊的任务，任务是一种特殊的对话，只是产出不同。

这句话把问题拉到最底层。现在的代码有两个「态」：

```
纯对话态 → for 循环 + decide + respond
执行态   → if-else + control/waiting/enqueue
```

`active_plan` 不是 Planner 的输入字段，而是路由分支的条件。所以「执行态」下群聊死了——用户问「做得怎么样了」被 `enqueue_note` 塞进 worker 备注。

**应该怎样**：`active_plan` 跟 `transcript` 一样——有就有，没有就没有。Planner 自己看着办。ChatService 不需要知道现在是什么态。

---

## 转折点 4：用户说「为什么要 pause？这难道不是工作的一部分吗」

> 你问我问题，我不会一声不吭直接做。问问题、等答案、讨论——全是工作的一部分。一旦 pause，反而需要一个显式让他 run。

这句话拆掉了 PAUSED 的根基。

PAUSED 的逻辑是：worker 问问题 → 进入特殊状态 → 等外部信号 → 被唤醒。但现实中，你问问题 ≠ 你暂停了工作。你只是在等输入。**等输入是工作的自然组成部分，不是例外状态。**

所以任务状态应该是两种，不是七种：

```
DONE     ← task_complete → 验收通过
NOT DONE ← 其他一切（写代码、等人、讨论、卡住、思考）
```

Harness 不需要区分 NOT DONE 里的各种情况。它只关心一件事：交卷了没有。

---

## 转折点 5：用户说「能不能不要超时自动决策，而是再发一次消息提醒」

原本计划加 wall-clock 超时。超时后强制 worker 自行决定继续。

**用户纠正**：不要替 worker 做决定。卡住了就提醒——再发一条消息到群聊。「XX 还在等你的回复」。

但进一步讨论后，觉得**时间维度不如对话轮次维度**。不是 5 分钟没人回就提醒，而是 3 轮对话过去了还没人理 worker 的问题就提醒。

这个提醒不依赖任何新机制——`decide` 已经能看到 transcript，自然知道「有人在等、没人回答、对话已经走了几轮」。

---

## 收敛：不变的东西

整个推理链条改变的都是**外层边界**——路由、协议、状态粒度。但有三样东西从头到尾没变：

1. **一个大脑，两种视野**：Planner 是唯一 LLM 决策点
2. **决策层统一，执行层不统一**：respond 轻执行 / work 重执行
3. **Harness 是确定性骨架，零 LLM**：图遍历 + FSM + 验收命令

变的只是：任务状态从 7 种收成 2 种、Worker 说话从专用 tool 回归正常文本流、「谁在等答案」从 Harness 的责任回归 Planner 的责任。

根本驱动力不是「更简单」——是「更像人工作的方式」。
