# 群聊讨论模式 — 问题与方案对比

> 日期: 2026-05-25 | 基于调研结论，对比 AgentHub 的可行方案

## 问题 1: 上下文过时

**场景:** 用户说"这个 bug 怎么修"，AgentA 2 秒回复"前端问题"，AgentB 8 秒才回——但 B 的上下文里没有 A 的回复，可能给出矛盾诊断。

| 方案 | 做法 | 优点 | 缺点 | 业界参照 |
|------|------|------|------|----------|
| **A: 回合制** | 协调者控制发言顺序，一次一人说话，说完广播，再选下一个 | 天然无并发、无过时、Agent 互知 | 延迟累积(3 Agent × 5s = 15s) | AutoGen GroupChat |
| **B: 等齐再发** | 等所有 Agent 回复完，一次性展示 | 用户看到的是完整讨论结果 | 最慢的拖慢所有人，体验差 | — |
| **C: 放任并发** | 各回各的，用户自己判断。多回复按完成顺序上屏 | 响应快 | 可能重复/矛盾，用户需要后续澄清 | Slack Agents (2026) |
| **D: 协调者汇总** | 协调者收集所有回复→合成为一条→只推这一条 | 用户只看到一条结论 | 协调者本身增加延迟，且需要足够的 LLM 能力 | Slack Director's Journal |

## 问题 2: 谁该回应

**场景:** 用户说"按钮点不了"，群里有前端专家、后端专家、文案。谁该回？

| 方案 | 做法 | 优点 | 缺点 | 业界参照 |
|------|------|------|------|----------|
| **A: 规则匹配** | 消息关键词匹配 Agent 的 `capability_tags` | 确定性强、可审计、零额外成本 | 规则维护成本随 Agent 增多上升 | botinabox, Discord bots |
| **B: LLM 判断** | 每次消息让轻量 LLM 判断"谁该回" | 最灵活，适应复杂语义 | 额外 LLM 调用成本，结果不可预测 | AutoGen `speaker_selection="auto"` |
| **C: 协调者调度** | 用户消息先发协调者→协调者决定分配给谁 | 协调者可以做任务分解+分配 | 增加一步延迟，协调者需要足够能力 | AutoGen GroupChatManager |
| **D: 全员自决** | 消息发给全体，Agent 在 system prompt 中判断是否回复 | 无中央决策点 | 噪声大，Agent 容易过度回应或沉默 | YES AND (CHI 2025) |

**推荐:** 分层路由 — 先 @mention 定向（用户显式指定），再关键词规则（确定性兜底），最后 LLM 兜底（复杂场景）。纯 LLM 决策在生产中不够稳定。

## 问题 3: Agent 回复是否通知其他 Agent

**场景:** AgentA 回复了"是前端问题"，AgentB 需要知道吗？知道=可能循环，不知道=可能重复劳动。

| 方案 | 做法 | 优点 | 缺点 | 业界参照 |
|------|------|------|------|----------|
| **A: 不通知** | Agent 回复只上屏，不发给其他 Agent | 零循环风险 | Agent 之间互不知情，可能重复劳动 | Discord Bot |
| **B: 回合内广播** | 当前 Agent 回复完→广播→协调者判断是否继续→选下一个 | Agent 互知，回合制天然防循环 | 延迟，依赖协调者判断终止时机 | AutoGen GroupChat |
| **C: 追加到历史** | Agent 回复落库后，仅作为后续消息的上下文追加，不触发新一轮 | 不循环，后续消息有完整历史 | 只对后续新消息生效，不影响当前轮 | — |
| **D: 结构化传递** | Agent 之间通过 Task 对象传递信息，不读彼此原始聊天 | 安全，可审计 | 上下文缺失，灵活性低 | CrewAI |

## 综合方案矩阵

| 组合 | 上下文 | 路由 | 通知 | 延迟 | 复杂度 | 推荐场景 |
|------|--------|------|------|------|--------|----------|
| 回合制 | A | C | B | 中(10-20s) | 中 | 需要多 Agent 协作讨论 |
| 分层路由+并发 | C | A→B | A/C | 低(3-8s) | 低 | V1 快速交付 |
| 协调者汇总 | D | C | D | 高(15-30s) | 高 | 需要精确结论的场景 |

## AgentHub 推荐路径

```
V1 (本期):  @ 路由模式（已完成设计，见 docs/design/group-chat_群聊功能设计方案.md）
            用户显式 @Agent → 单 Agent 回复
            不存在"谁该回""上下文过时""多 Agent 通知"问题

V2 (M3):    回合制讨论模式
            协调者选人 → 一人发言 → 广播 → 再选 → 终止
            天然解决三个问题，代价是延迟
            用户可切换 @模式/讨论模式
```
