## CE-001 [BP-004 一键安装 - 并发安装同 MCP]

- **关联流程**: BP-004
- **失效场景**: R-03 在 1 秒内点击"安装"两次，触发并发创建 instance
- **根因分析**: F-004 验收③要求幂等但未明确"幂等键检测时点"，并发场景下两请求同时通过 `unique(user_id, mcp_id)` 检查前各自创建
- **影响范围**: 同一用户产生 2 个 instance_id，绑定时路由冲突
- **当前处理能力**: 部分（数据库唯一约束兜底但产生 race condition 日志噪音）
- **建议修复**: BP-004 步骤 2 改为分布式锁（`SELECT ... FOR UPDATE` 或 Redis SETNX），并发时第二个请求直接返回已有 instance

## CE-002 [BP-008 版本管理 - CVE 紧急更新触发 LRU 清理]

- **关联流程**: BP-008
- **失效场景**: MCP 有 50 个历史版本，pinned 49 个 + 1 个紧急 CVE patch；LRU 清理时仅看 `is_pinned` 字段
- **根因分析**: R-004 允许 CVE 紧急更新绕过主版本号提升，但 LRU 清理策略未考虑"紧急 patch 重要性"
- **影响范围**: 紧急 patch 被误清理，R-03 升级时找不到该 patch
- **当前处理能力**: 不能
- **建议修复**: DE-003 增加 `is_critical_patch` 字段；LRU 清理跳过 `is_pinned OR is_critical_patch`

## CE-003 [BP-009 Agent 绑定 - 工具名 hash 碰撞]

- **关联流程**: BP-009
- **失效场景**: 多个 MCP instance 截断后产生相同的 `server_slug_32 + tool_28 + hash_6` 命名
- **根因分析**: S-035 截断规则用 MD5 6 字符后缀，理论碰撞概率 1/16M
- **影响范围**: 同一 Agent 绑定两个 MCP 出现同名工具，运行时冲突
- **当前处理能力**: 不能
- **建议修复**: 截断后写入前做 `(agent_id, tool_name)` 唯一性校验，碰撞时扩展 hash 到 8 字符

## CE-004 [BP-012 CLI Adapter - 注入后 Runtime 立即崩溃]

- **关联流程**: BP-012
- **失效场景**: ClaudeCode 收到 `claude mcp add` 后立即崩溃（PID 消失），Agent 启动时无 MCP 工具
- **根因分析**: F-012 验收③允许"注入失败 Agent 仍可启动"但未规定"Runtime 立即崩溃"的处理路径
- **影响范围**: R-03 在 IM 中调用工具时返回空白（无 error_code）
- **当前处理能力**: 部分
- **建议修复**: BP-012 步骤 6 增加 Runtime 健康检查（30s 周期），Runtime 崩溃时发 WebSocket 事件 `runtime_unhealthy`

## CE-005 [BP-014 WebSocket - 50 并发 tool_call 触发 ack 重发风暴]

- **关联流程**: BP-014
- **失效场景**: 50 并发 tool_call 同时失败，触发 50 个 ack 5s 重发，WebSocket 连接拥塞
- **根因分析**: S-054 重发策略无并发控制
- **影响范围**: 99.5% 投递率 SLO 失效
- **当前处理能力**: 不能
- **建议修复**: 重发加令牌桶限流（100 req/s），超过时排队 + 告警

## CE-006 [BP-020 dry-run - 沙箱后端不可用时静默降级]

- **关联流程**: BP-020
- **失效场景**: Windows Home 缺 WSL2，Docker 不可用，cgroup v2 不存在；setrlimit 也被 S-049 标记需降级警告
- **根因分析**: R-023 验证 WSL2 cgroup v2 一致性 ⚠️，EX-050 仅警告未拒绝入库
- **影响范围**: 危险 MCP 通过 dry-run 实际无隔离直接入库，运行时 RCE
- **当前处理能力**: 不能
- **建议修复**: 沙箱后端不可用时 R-01 强制阻断 dry-run，R-02 必须升级环境

## CE-007 [BP-018 sse/http - DNS 重绑定跨对象失效]

- **关联流程**: BP-018
- **失效场景**: URL 解析用 yarl 锁定 IP=1.2.3.4（合法），HTTP 302 重定向到内网 URL，yarl 跨对象失效重解析为 127.0.0.1
- **根因分析**: R-026 验证 yarl Pinning 仅在单个 URL 对象生命周期内有效
- **影响范围**: SSRF 攻击成功，访问内网服务
- **当前处理能力**: 不能
- **建议修复**: 实现域名级缓存 Resolver（DE-011 dns_pinning_enabled = true）；重定向后重新校验

## CE-008 [BP-021 模板库 - 用户自创 PostgreSQL 模板]

- **关联流程**: BP-021
- **失效场景**: R-02 看到 V1.3 模板移除 PostgreSQL 后，私下创建并发布"PostgreSQL 模板"到市场
- **根因分析**: RSK-01 已规避官方模板，但用户自创无审计
- **影响范围**: 用户下载含 CVE-2025-49596 的 PostgreSQL 模板被攻击
- **当前处理能力**: 不能
- **建议修复**: DE-018 模板发布必经 K4 静态分析，CVE-2025-49596 规则强制

## CE-009 [BP-022 schema 校验 - 工具名 64 字符边界]

- **关联流程**: BP-022
- **失效场景**: 工具名恰好 64 字符，但 server_slug 32 字符 + tool_name 28 字符 + 6 字符 hash = 66 字符，超限
- **根因分析**: S-035 截断规则边界未严格测试
- **影响范围**: 截断后仍 > 64 字符，Anthropic API 拒绝
- **当前处理能力**: 不能
- **建议修复**: 截断后强制 ≤ 64 字符，否则扩展 hash 长度

## CE-010 [BP-024 权限显式同意 - 用户跳过同意 UI]

- **关联流程**: BP-024
- **失效场景**: R-03 同意 UI 加载缓慢（5s），用户直接点击"同意"按钮；权限文本快照未完整记录
- **根因分析**: DE-013 consent_text 字段需 UI 完整渲染后写入，但前端事件触发时序可能早于异步加载
- **影响范围**: 审计追溯时无法证明 R-03 同意了哪些权限
- **当前处理能力**: 部分
- **建议修复**: 前端同意按钮在 UI 完整渲染前 disabled；后端校验 consent_text 长度 > 阈值

## CE-011 [BP-026 重试降级 - 取消与重试冲突]

- **关联流程**: BP-026
- **失效场景**: R-03 在重试 2s 等待期间点击"取消"，重试逻辑未感知取消
- **根因分析**: S-065 禁用 idempotency_key 防双花，但未明确"取消时如何停止正在等待的重试"
- **影响范围**: 取消后仍执行 1 次重试，违反"取消请求 2s 内到达 Runtime"
- **当前处理能力**: 不能
- **建议修复**: BP-026 步骤 2 加取消标志位；重试前检查 cancel_token

## CE-012 [BP-029 告警 - 5min 窗口边界]

- **关联流程**: BP-029
- **失效场景**: 告警在 12:04:59 触发，5min 去重窗口结束于 12:09:59；12:09:58 再次触发时被错误地认为"已去重"
- **根因分析**: S-066 dedup_key 设计未明确时间窗边界
- **影响范围**: 同 MCP 同错误类型在窗口边缘触发两次告警
- **当前处理能力**: 不能
- **建议修复**: dedup_key 增加 minute_bucket，窗口严格以分钟为粒度

## CE-013 [BP-014 + BP-016 联动 - ack 重发导致审计日志重复]

- **关联流程**: BP-014 + BP-016
- **失效场景**: tool_call_response 重发 3 次，审计日志写 3 条
- **根因分析**: BP-014 重发与 BP-016 审计日志写入无去重协调
- **影响范围**: 审计统计不准确（DE-009 计数虚高）
- **当前处理能力**: 不能
- **建议修复**: DE-008 event_id 作为审计去重键，审计写入前 SELECT 已存在则跳过

## CE-014 [BP-009 + BP-005 联动 - 卸载时绑定状态不一致]

- **关联流程**: BP-009 + BP-005
- **失效场景**: R-03 卸载 instance（BP-005），同时另一个会话尝试绑定同一 instance（BP-009）
- **根因分析**: 两个流程对 `instance.status` 的读写无并发控制
- **影响范围**: 绑定成功但 instance 实际已卸载，tool_call 路由到不存在的 instance
- **当前处理能力**: 部分
- **建议修复**: BP-005 + BP-009 共享 `instance_id` 维度的分布式锁
