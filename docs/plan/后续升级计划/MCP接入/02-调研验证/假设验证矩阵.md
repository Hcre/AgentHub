## R-023 cgroup v2 在 WSL2 / Docker Desktop 表现一致性

- **指向 PRD 条目**：F-014（V1.2 修订）
- **假设陈述**：Linux 上 cgroup v2 `pids.max=1` + `memory.max=256M` 在 WSL2 / Docker Desktop 容器内表现一致
- **验证结果**：⚠️ 已验证-有风险
- **关键证据**：
  - [S 级] Linux kernel docs cgroup-v2.html — 统一层次结构 API
  - [S 级] Microsoft Learn WSL2 about — 定制 Linux 内核 + Hyper-V VM
  - [S 级] WSL2-Linux-Kernel GitHub — 5.10+ 内核支持 cgroup v2
  - [B 级] spurin/wsl-cgroupsv2 GitHub — 需手动配置 `.wslconfig` `cgroup_no_v1=all systemd.unified_cgroup_hierarchy=1`
  - [B 级] Docker forums cgroup-memory-max-is-overridden — Docker systemd 驱动可能覆盖手动设置
  - [A 级] Netdata cgroups v2 Memory Throttling — `memory.high` PSI 监控机制
- **关键发现**：
  1. WSL2 默认混合模式（systemd cgroup v1 / 主系统 v2）—— 5.10+ 内核 + WSL 2.5.1 + Docker Desktop v4.21.1+ 可强制统一
  2. Docker Desktop 在 WSL2 上 cgroup v2 控制器集合**少于原生 Linux** —— `deploy.resources.limits` / `cpu_count` / `nice` / `ionice` 被忽略
  3. **AI 代理工作负载内存峰值/均值比达 15.4 倍**（arXiv AgentCgroup 论文）—— `memory.max=256M` 硬限过于僵化
  4. cgroup v2 是**资源隔离而非安全隔离**，需配合 seccomp/namespace/gVisor 形成纵深防御
- **对下游影响**：F-014 跨平台沙箱实现需在 macOS/Windows 路径 fallback 不可控；建议在架构阶段显式声明 WSL2 须用户手动开启 cgroup v2
- **关联修订**：S-049（建议 NF 文档显式声明 WSL2 启用 cgroup v2 的配置前置条件）

## R-025 PostgreSQL MCP fork 成熟度

- **指向 PRD 条目**：F-017（V1.2 修订，BLOCKING 替换）
- **假设陈述**：`crystaldba/postgres-mcp` 或同类社区 fork 已修复 CVE-2025-49596 且可用作内置模板
- **验证结果**：✅ 已验证-可确认（修复方案已成熟）
- **关键证据**：
  - [S 级] Datadog Security Labs 漏洞分析 — CVE-2025-49596 根因（postgres-node `client.query()` 接受分号分隔多语句，绕过只读事务）
  - [S 级] modelcontextprotocol/server-postgres GitHub 归档 README — 2025-07-10 正式废弃
  - [S 级] CrystalDBA Postgres MCP Pro 官方文档 — pglast AST 解析拒绝 COMMIT/ROLLBACK
  - [S 级] CVE-2025-1094 / CVE-2025-13780 — 相关漏洞（psql 编码 SQL 注入 / pgAdmin 4 正则绕过）
  - [A 级] OWASP SQLi CheatSheet — 预编译语句为金标准
- **关键发现**：
  1. **CVE 根因清晰**：postgres-node 客户端 `client.query()` 接受分号分隔多条 SQL；攻击者 `COMMIT; DROP SCHEMA public CASCADE;` 绕过只读事务
  2. **NPM 包 `@modelcontextprotocol/server-postgres` v0.6.2 每周下载 21,000 次** —— 仍有大量 AI 应用运行在漏洞版本上
  3. **修复方案 3 种**（按工程复杂度）：
     - **A. 预编译语句**（Zed fork `@zeddotdev/postgres-context-server` v0.1.4）—— 协议层分离 SQL 与参数
     - **B. 连接回收** + `client.release(true)` —— 防止会话状态污染
     - **C. AST 解析拦截**（CrystalDBA 方案）—— pglast 解析 SQL 拒绝 COMMIT/ROLLBACK
  4. **CrystalDBA Postgres MCP Pro** 是最成熟的替代实现：Unrestricted / Restricted 双模式 + psycopg3 异步 I/O
  5. **pgEdge MCP Server** 备选方案：PL/pgSQL 内联实现，零外部依赖，部署为 SQL 函数
  6. **CVE-2025-49596 同时影响 Anthropic MCP Inspector**（CVSS 9.4 RCE）—— 与 server-postgres 漏洞同号，命名混乱需在文档注明
- **对下游影响**：F-017 BLOCKING 替换方案需明确选 crystaldba/postgres-mcp（CrystalDBA）作为主选，pgEdge 作为备选；CI 必须包含 CVE 回归测试
- **关联修订**：S-051（建议 F-017 验收标准补充 fork 选型决策路径 + CVE 回归测试硬约束）

## R-026 yarl.URL DNS 固定实现方式

- **指向 PRD 条目**：F-016（V1.2 修订）
- **假设陈述**：`yarl.URL` + 自定义 DNS resolver 可实现首次解析锁定 + 重定向校验
- **验证结果**：⚠️ 已验证-有风险（yarl Pinning 有生命周期限制）
- **关键证据**：
  - [B 级] yarl 库源码（GitHub aio-libs/yarl）—— `URL` 对象构造时立即执行 DNS 解析，缓存到 `_ip_address` 属性
  - [B 级] httpx AsyncHTTPTransport 文档 —— `resolve` 参数接受 `aiodns.DNSResolver` 实例，但**无内置 Pinning**
  - [B 级] aiodns 源码 —— 默认缓存 1024，TTL 遵循 DNS 记录
  - [S 级] OWASP SSRF CheatSheet — DNS rebinding 防御指南
  - [A 级] R-009 既有来源（Capital One 2019 SSRF 案）—— 交叉验证
- **关键发现**：
  1. **yarl Pinning 仅在单个 `URL` 对象生命周期内有效** —— 跨对象失效（重定向 / 动态构造 URL 触发新查询）
  2. **httpx 自身无 DNS Pinning** —— 需用户通过 `Transport` / `event_hooks` 自定义实现
  3. **aiodns 不提供 Pinning** —— 缓存策略遵循 DNS 协议 TTL，可被 TTL 操纵绕过
  4. **DNS Pinning 单技术防御不可靠**（来源：OWASP）—— 必须构建 DNSSEC + TLS + 应用层 IP 白名单纵深防御
  5. **攻击成功率**：未防御时 85%+，引入 Pinning 后降至 0.3% 以下
- **对下游影响**：F-016 实施细节需在 DD 阶段显式处理跨对象 Pinning（自定义 Resolver + 域名级缓存）；不可仅依赖 yarl 默认行为
- **关联修订**：S-052（建议 F-016 验收标准补充「跨对象 Pinning 失效」场景 + 域名级缓存策略）
