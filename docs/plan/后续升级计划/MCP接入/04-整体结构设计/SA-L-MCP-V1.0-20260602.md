## 0. 架构模式选择（soul 4.8 决策）

```
[选定模式] 分层架构（核心骨架）+ 事件驱动（审批/通知通道）+ 插件化（MCP市场/MCP模板）
[选择理由]
  1) 系统含 4 个清晰功能主题（市场/绑定/创建/安全审批），主题数 = 4 — 介于分层(≤3)与微服务(≥5)之间
  2) 主题间耦合度中等（BP-019 审批被 BP-002/007/016 触发，BP-009 config 被 BP-007/010 触发）
     → 分层架构保证职责清晰，事件驱动解耦跨主题耦合
  3) 业务关键路径含 4 个事件触发点：① 审批超时（BP-020）② 模板迁移到期（BP-024）③ webhook 升级（BP-017）④ healthcheck 状态变更（BP-005）
     → 事件驱动为最自然的选择
  4) MCP 市场 + 5 个内置模板为典型"核心+扩展"模式——核心平台 + 插件化 MCP server
     → 插件化预留未来扩展
[模式约束] （soul 4.8.2 一致性约束）
  - 分层：每层仅依赖下层，禁止同层调用
  - 事件驱动：模块仅发布/订阅事件，不直接调用审批/通知
  - 插件化：核心定义 RuntimeInterface / ToolNameSpec / SandboxBackend 三类 SPI
```

## 3. 逻辑视图（备选方案）

> 备选方案仅在此处对比列出，详见 AC-MCP-V1.0-20260602.md 方案对比报告

**备选方案 — 微服务架构**
- 按业务域拆分为 5 个独立服务：市场/绑定/创建/审批/进程池
- 进程池服务独立为可水平扩展的 Operator
- 服务间通过 REST + 消息队列通信
- 优势：单服务可独立扩缩容（BP-022 池满场景压力增大时可单独扩进程池 Operator）
- 劣势：增加运维复杂度（5 个独立部署单元）；沙箱+SSRF+K4+MCP 创建耦合紧密，强行拆分会引入分布式事务

**架构模式决策 → 选定主方案：分层 + 事件驱动 + 插件化**（详见 ADR-001）
